# `api/.htaccess` — locking the door

> A tiny but essential file. It tells the web server what visitors are **not**
> allowed to open.

## What it does

cPanel runs **Apache**, a web server that reads `.htaccess` files for rules.
Ours says:

```apache
<FilesMatch "^(config\.php|config\.example\.php|db\.php)$">
    Require all denied
</FilesMatch>
```
If anyone types `gilleadsafaris.com/api/config.php` in a browser → **403 Forbidden**.
Only `submit.php` can be reached from outside. `config.php` and `db.php` can
still be *used* by `submit.php` (via `require`) — PHP reads them from disk, not
through the web.

```apache
Options -Indexes
```
Without this, visiting `gilleadsafaris.com/api/` could show a list of every
file in the folder. Now it shows nothing.

## Why this matters even though PHP files don't show their code

Normally the server *runs* a `.php` file rather than showing it. But if PHP
ever breaks or is misconfigured, the raw file — **with your database
password** — could be displayed. `.htaccess` is the second lock on the door.
Security works in **layers**: config outside Git, config blocked from the web,
real passwords only on the server.

## Try it yourself (after uploading to cPanel)

1. Visit `https://www.gilleadsafaris.com/api/config.php` → expect **403 Forbidden**.
2. Visit `https://www.gilleadsafaris.com/api/` → expect no file list.
3. Visit `https://www.gilleadsafaris.com/api/submit.php` → expect
   `{"ok":false,"error":"Use POST."}` — reachable, but only does its job for POST.

*(Your Mac's built-in `php -S` test server ignores `.htaccess` — that's why
these checks only make sense on the real server.)*
